# Remote EX development test bundle

**Development preview, not a signed production installer or an unattended access service.** This bundle contains the app and locally built LAN and routed media programs. The GStreamer runtime is NOT redistributed; install the official, architecture-matched GStreamer 1.26.11 runtime separately from https://gstreamer.freedesktop.org/download/ (choose old stable 1.26). On Windows, use the MSVC x86_64 runtime and ensure its bin directory is in PATH. On macOS, use the official universal runtime. Do not mix runtime architectures or third-party plugin trees. Dependencies and distribution obligations remain under review.

Extract the archive. On macOS open Remote EX.app (the media programs are inside Contents/MacOS); on Windows keep the files in the same directory and start remote-ex-desktop.exe. Do not move or replace any media program independently. BUILD_INFO.txt identifies the actual source commit and runtime version. The GUI supports encrypted view-only sharing, diagnostics and experimental control (30-second limit). Both peers must compare the complete displayed key bundle independently and explicitly approve. Keep the host UI visible and use Disconnect. Grant OS screen-recording permission normally if prompted; no elevated privileges or privacy bypass.

## Native control prototype
Choose Remote control (experimental) on both desktop applications. Select roles and the host's primary display. Independently verify the full key bundles and explicitly grant screen and input access. Keep the host UI visible. Disconnect requests graceful revocation and reports release confirmation or failure. Requires native-control build, both owned/authorized devices, matching primary display coordinates and ordinary OS permissions. Alternatively, use the visible terminal prototype from the extracted directory on Windows, or the app's Contents/MacOS directory on macOS, on the host:
```
./lan_control --listen PRIVATE_IP:PORT --control DISPLAY_ID
```
On the controller:
```
./lan_control --connect PRIVATE_IP:PORT --control
```
Windows PowerShell: use .\lan_control.exe instead. Select the host primary display ID using the app's local display diagnostics. Independently verify both complete key bundles; the host explicitly confirms screen AND input, the controller explicitly confirms input. Approve host first. The host must keep the visible terminal; Ctrl-C revokes, Escape or closing the controller window disconnects. Native window forwards input only when focused and within the picture content. Do not expose the listener to the Internet or enable port forwarding. Sessions are limited to 30 seconds, no automatic reconnect or unattended control. Normal stop requests release tracked keys/buttons before acknowledgement; sudden kill, OS failure, or a blocked platform capture can delay or prevent cleanup. Do not rely on this prototype for critical systems.

CI verifies synthetic/inert tests only. Actual physical-device display capture, GUI, key mapping/DPI, and native input behavior still require authorized local testing. The Windows binaries are unsigned, macOS binaries only ad-hoc signed; no notarization or release. Do not bypass OS security policies. Development build uses GStreamer 1.26.11 SDK for reproducible testing, not a security-audited frozen release configuration.

The macOS development app embeds the official framework's standard runtime search path in the media executables. It does not bundle or install the framework; use the official GStreamer package. The app is ad-hoc signed only and is not notarized. A successful package verification does not replace launch, TCC, or two-machine testing.

LAN signaling explicitly restores blocking mode on an accepted TCP stream before applying its bounded read/write deadlines. This corrects the Windows Winsock inherited nonblocking-mode failure observed in the first full native build. The new development build must pass the actual encrypted control tests before publishing artifacts.

## M3 development candidate

This candidate adds device groups, favorites, optional connection history, time-limited invitation hints, video quality presets, resizable viewer, explicit one-shot text/image clipboard and single-file exchange, in-session file pause/resume, separate audio, three independent controller slots and transport statistics. The physical host still explicitly approves each operation. File receiver selects a new local path; overwrite is refused. Limits: file 64 MiB, text 64 KiB, PNG 4 MiB / 2048x2048; pause does not outlive the current authorized session. Real screen/input/audio sessions retain the 30-second development limit. System audio capture is experimental Windows WASAPI loopback only; playback Windows/macOS. No combined audio/video session or macOS system capture. View-only supports non-primary selection; native control remains primary display. Multiple concurrent controllers require separately enrolled identities; content-sharing/host sessions are exclusive. Invitations are not credentials. Missing full-screen/toolbar, live display switch, remote file manager, drag-and-drop, restart-resume, automatic clipboard, and shared-identity session multiplexing remain open. No physical-device PASS or performance guarantee. See M3_FULL_HANDOFF.md. New packages require actual successful CI; previously published artifacts do not contain M3.

## M3 fourth integration batch

The latest candidate optionally shares the original slot-one persistent signing identity across up to three outgoing test/view/control sessions. Enable the shared ID option in each participating slot, then enroll that single ID on the updated WSS service. The server uses a separately domain-signed controller-only registration and tracks session ownership by exact authenticated connection. Ordinary registration (including host and presence) remains exclusive; controller-only sockets cannot be incoming targets. Separate device IDs remain supported. Do not run presence for the same ID concurrently. Each session still needs independent local consent. This requires the updated server; no downgrade or automatically resumed grant.

The candidate also includes explicit file checkpoint recovery, whole-directory transfer, local drag-to-select, independent 30-second text clipboard sync and a read-only remote file catalog. For catalog mode the host chooses one bounded local root (256 entries, 8 levels, aggregate 64 MiB) and explicitly permits listing and one file download. Controller chooses a new local destination, views the relative manifest, selects a file by index and clicks Download. No arbitrary remote paths, rename, delete, overwrite, or remote execution. Initial clipboard contents are not sent; no real OS clipboard is read by synthetic tests. The new full development build must pass native compilation and runtime tests; earlier M3 artifacts 04b1cfd do not contain these features. The same external GStreamer runtime and physical-device gates apply.

## M3 sixth integration batch

Remote files (reviewed changes) is a distinct one-shot profile. The host explicitly selects a local root and grants only the ability to propose changes. The controller chooses a maximum of four operations using the authorized catalog, then the host reviews exact relative paths and explicitly approves the pending batch. Supported: create an empty directory/file, rename a regular file to a new unused name in the same directory, move a regular file to a new local Remote-EX-Recovery directory. No recursive deletion, existing-file overwrite, directory rename, remote arbitrary paths or automatic execution. Recovery content is ordinary local data; keep or remove it locally as appropriate. Filesystems without hard links may refuse rename/recovery without removing the original. Partial failure is possible; inspect the reviewed destination/recovery paths, no automatic rollback. Do not operate in important live folders pending physical and platform safety acceptance. cap-std 4.0.3 introduced for capability-relative access (upstream Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT; complete licensing review pending). The fifth-batch artifacts 1463dfb passed actual synthetic A/V and include compiled macOS helper; they do not contain this sixth-batch feature. New packages require successful platform fixture tests and artifact upload.


## M3 seventh integration batch
Remote files (batch download) is separately authorized and signed (profile 20). Select one to four files from the approved immutable catalog; the receiver chooses a new absolute directory path. Only selected files and their necessary parent directories are included; paths and sizes must match the selection before extraction and transfer SHA-256 is checked. Maximum total bundle size 64 MiB; no overwrite. A local failure or cancellation may leave a partially created new directory, which is reported and not automatically removed. The previous one-file and reviewed-change profiles are unchanged. New automated results and physical-device acceptance are pending.

## M3 eighth integration batch
Reviewed changes now support regular files and directories, with exclusive same-volume relocation and a separately reviewed Restore action for a top-level recovery entry. The controller chooses an unused name and destination parent under the approved root; the host reviews exact paths and subtree counts/bytes. No overwrite, permanent deletion, automatic restore location, or automatic cleanup. Unsupported filesystem operations fail; overlapping changes are rejected. Windows uses locally checked absolute names for exclusive move, and malicious concurrent local filesystem mutation is outside the verified boundary. New CI and physical-device acceptance pending.
